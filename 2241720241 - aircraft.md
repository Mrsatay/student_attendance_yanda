#### Chapter 1 Introduction

#### 1.1 Background of the Study

Most planes go through tough checks before they fly regularly. When problems pop up midair, they can be small glitches or big hardware issues. Fixing them right matters a lot – it keeps flights safe, meets legal rules, and makes sure the machine works as needed. Every single problem found gets logged, looked into closely, handed off for fixes, then confirmed solved prior to moving ahead [8][10]. Most flight testing setups still handle breakdown reports using old – school paperwork, basic spreadsheet files, or separate software bits that do not talk to one another. Because of this split system, details get lost – some stored here, some saved elsewhere, while real-time changes rarely make it into every log. Without a central window showing what problems remain unsolved, who has been assigned what task, or which deadlines have passed, teams struggle to track how fast issues are being fixed. Missing this big-picture insight tends to muddy judgment, slowing down tests more than necessary. A system where each discovered issue gets followed closely from start finish that is what closed-loop management means. From first detection right through to confirmed resolution, nothing slips away unnoticed. Each step stays recorded so people can check back later if needed. Instead of dropping problems midway, they move steadily toward closure. When used during airplane testing, tracking faults this way brings clearer records. Processes become more consistent across teams and tasks. Information flows openly because very decision leaves a mark. Nothing hides in the background once this method takes hold [8].

#### 1.2 Problem Statement

Despite the crucial nature of fault management in aircraft testing, there are companies that depend on unstructured and partially structured methods that suffer from the following disadvantages: (1) The absence of centralized information about the faults: Fault information can be scattered across different tools and documents, and therefore, it is challenging to acquire up-to-date information about all faults. (2) The absence of a defined workflow for processing faults: Since faults cannot be handled using a defined workflow, certain stages of investigating faults may be ignored. (3) Difficulty in tracing faults: There is an inability to record any changes in the status and owners of faults in the process of managing faults. (4) Poor reporting: Without reporting tools, it is not easy to generate reports for the faults' trends, overdue work, and subsystems. (5) Manually documenting faults: Documentation of faults takes a lot of effort because engineers have to manually prepare fault descriptions and summaries.

#### 1.3 Project Objectives

The main objective of this project is the development and implementation of the Aircraft Test Fault Closed-Loop Management System on the web platform which will overcome the shortcomings outlined above. The specific objectives of this project are as follows: (1) To develop a fault management web-based platform where the users can create, read, update and manage the life cycle of the faults. (2) To incorporate a controlled closed-loop process where each fault must go through predefined status transitions before reaching the end point. (3) To implement a role-based security feature which will determine the permissions that each user type enjoys. (4) To develop a status tracking functionality where the user can track all the status changes that have been made in a particular record. (5) To develop a dashboard reporting module which displays fault statistics, subsystem distributions and trends. (6) To implement an artificial intelligence-based assistance program that helps the engineers to create fault descriptions and explanations.

#### 1.4 Scope of the System

Project Scope will be: (1) The system will be used for an aircraft test fault management scenario that will assist test engineers, maintenance engineers, and test managers. (2) The system will run as a web application using the Django Framework with PostgreSQL DB and will be accessible via web browser without any client side setup. (3) Fault workflow will have seven defined stages that are New, Assigned, Analysis in Process, Root Cause Found, Under Fixing, Resolved and Closed. (4) The user roles will be limited to only four roles including Admin, Test Engineer, Maintenance Engineer, and Test Manager. The roles will have certain privileges associated with different functionalities of the system. (5) The AI assistance will help in describing faults and providing explanation. For this, we will be using OpenRouter API as the AI source. However, there will be a local template fallback in case of unavailability of external sources. (6) The system will be devoid of any integration with external aircraft components and sensor information. Faults would all be entered manually. (7) The report and dashboard view functionalities will be read only and will depend on the data stored in the system database.

#### 1.5 Significance of the Project

The value of this project lies in its contribution to improving the way faults are managed in aircraft testing by providing a systematic digital solution. To understand the significance of the project, one must consider its significance from the following perspectives: On the operational level, this project provides a closed-loop mechanism that guarantees the proper tracking of faults. This mechanism helps ensure that all problems are properly solved because the use of roles makes sure that each step in the fault workflow is taken exclusively by an authorized person. On the management level, this project offers dashboards and reporting features that give the ability to instantly see the current status and get insights about potential problems, problematic aircrafts, overdue tasks, etc. On the technical level, the project provides assistance in documenting faults via AI that reduces the time needed for writing the description and the summary after solving each problem. On the academic level, the present research proves the applicability of the software engineering concepts like using Django for developing web applications, creating a relational database via PostgreSQL, following the REST paradigm for interacting between components, and implementing AI-assistance services [6][9][11].

#### 2.1 Python and Django Framework

Python is a general-purpose, high-level programming language with wide-ranging applications in web development, data analytics, automation, and machine learning. This high level of readability, standard library, and vast number of third-party extensions make it suitable for development of advanced web applications. The entire backend logic is programmed using Python [1][7]. Django is a full-stack development framework written using Python language and based on Model View Template architecture. Django comes equipped with multiple out-of-the-box capabilities including an object-relational mapper, URL dispatcher, templating system, forms framework, and admin panel. The overall approach of the framework is driven by the philosophy of rapid development and don’t repeat yourself (DRY) [1][7]. In this case study, Django was selected as a backend framework due to its inherent support for complicated data models necessary for the fault management industry, ready authentication and session management, and module-wise separation of accounts, faults, aircrafts, dashboard, reporting, and AI functionalities.

#### 2.2 PostgreSQL Database

PostgreSQL is an open-source, object-relational database management system that boasts its adherence to standards, extensibility, and complex query capability. It offers excellent foreign key, join, transaction, and ACID-compliance features, which make it an ideal choice for building production applications using the relational database structure [2]. For this project, PostgreSQL will be used as the primary storage engine for storing all entities within the system, such as users, aircraft, faults, and status history. The relational model of fault data, in which faults have a one-to-one relationship with aircraft, engineers who reported and assigned the faults, and status history, makes PostgreSQL an ideal choice compared to other simple solutions like flat files and NoSQL databases. Django's ORM helps abstract PostgreSQL by offering Python classes to define the database schema and perform queries without writing any raw SQL queries.

#### 2.3 Frontend Technologies: HTML, CSS, and JavaScript

The front-end part of the system has been implemented through widely recognized web development technologies, such as HTML, CSS, and JavaScript, that provide users with well-defined web pages that can be used without installing any additional software or plug-ins into existing web browsers. HTML (Hypertext Markup Language) is used to create a well-structured HTML code for each page containing tables, forms, menus, and content areas. CSS (Cascading Style Sheets) is used to control the visual representation of created HTML elements, including their formatting and responsive capabilities. JavaScript allows for the implementation of dynamic features at the client side, such as validating entered information, showing pop-ups, performing asynchronous requests to the server, and drawing charts based on the results.

In this particular project, JavaScript has also been utilized for making asynchronous requests to the AI tools module, thus enabling the generation of fault descriptions without reloading the whole page.

#### 2.4 Bootstrap

Bootstrap is an open source front end CSS framework created by Twitter that offers a suite of ready-made UI components, a responsive grid system, and utility classes to quickly build user interfaces. Bootstrap will ensure that everything is visually styled consistently throughout the site without having to write custom CSS styles for each element [3]. In the current project, Bootstrap is used to create the navigation bar, layout grids, form controls, buttons, alert boxes, modals, and data tables. Using the responsive grid from bootstrap will ensure that our interface works correctly depending on the screen size and will be able to run not only on desktop computers but also on tablets for field work. The bootstrap component library will also offer accessible and semantically correct markup for elements such as drop downs and status badges.

#### 2.5 Chart.js

Chart.js is a JavaScript visualization library that can generate interactive and responsive chart graphics on the web application canvas. There are multiple chart types like bar chart, line chart, pie chart, doughnut chart, and radar chart supported by Chart.js. Chart.js is an easy-to-use library for visualizing data on the client side without serverside rendering [4]. In the current project, Chart.js is utilized in the dashboard feature for generating fault distribution data visualizations. The fault distribution chart is a doughnut graph representing fault distribution among different subsystems, a bar chart illustrating fault occurrences among different aircrafts, and a bar chart representing fault distribution by flight phase.

#### 2.6 Role-Based Access Control (RBAC)

Role-Based Access Control (RBAC) is one of the most common access control systems which allows accessing only those resources which were provided by assigning certain roles to individual users. In case of RBAC system, permissions are allocated according to specific roles of particular users. This system helps to simplify security measures, prevent privileges escalation, and provides more transparent audit of available actions and rights [9][11]. For this project, RBAC was implemented via Django authentication system and the use of the custom UserProfile class containing the role attribute. There are four types of roles in this system: (1) Admin : full access to all system operations – user and aircraft administration, faults administration etc.

(2) Test Engineer: possibility to create new fault, modify its information, start workflow transitions on faults assigned to a test engineer. (3) Maintenance Engineer: possibility to modify analysis fields, make entries into the actions fields of a particular fault, and start transitions according to maintenance activities. (4) Test Manager: viewing all faults, approving their workflow transitions, ability to generate reports and view dashboard. Role-based restrictions are made at the view layer in Django application.

#### 2.7 AI Service Integration

Integrating artificial intelligence in web applications through API services is becoming easier. In our project, the AI assistance is delivered using the OpenRouter API that serves as an interface to multiple LLMs (large language models). Our ai tools module utilizes the OpenRouter API service to create fault descriptions based on structured fault metadata. Additionally, the module provides the creation of maintenance notes as an explanation for resolving the detected faults [5]. Integration is realized via the ai_tools module that is a Django application module and provides API endpoints for generating text based on AI generations request. The request itself is sent asynchronously by the frontend JavaScript client that sends the fault description to the server. The server then forwards a structured prompt to the OpenRouter API and gets the text back. If any issues with sending data to the external API occur, the ai_tools module generates its own text response based on structured fault data available. It enables graceful degradation of functionality and prevents application crashes when the external API cannot be reached [6].

Use of AI assistance is meant to minimize the cognitive load on engineers when creating documentation in order to get more consistent and comprehensive fault descriptions.

#### 3.2 System Architecture

It works using a hierarchical web application architecture. The user requests are forwarded from the browser to the view methods via the URL configuration by Django. The business rules are applied in the service layer, the data persistence is done via ORM models in PostgreSQL, and the AI functionality can be optionally used with OpenRouter.

Model Layer specifies persistent entities using Django ORM, while PostgreSQL is used for database access.

#### 3.3.6AI Tools Module

#### 4.8.3 AI Response Verification

This section evaluates the output of the Artificial Intelligence (AI) helper module used in the Aircraft Test Fault Closed-Loop Management System. The purpose of this verification is to ensure that the generated LLM answer is not only readable, but also correct, relevant, and supported by the original fault data stored in the system. In an aircraft testing and maintenance context, a technically fluent answer is not sufficient if it contains information that has not been verified by the engineer or recorded in the database The AI helper module is intended to assist engineers in preparing fault descriptions, maintenance explanations, and workflow-related summaries. It is not designed to replace engineering judgment or make autonomous maintenance decisions. Therefore, every AI-generated response must be evaluated before it is accepted as part of formal documentation. This evaluation focuses on whether the AI response accurately reflects the available fault record and whether it avoids unsupported assumptions. 4.8.3.1 Purpose of AI Response Verification The main purpose of AI response verification is to reduce the risk of hallucination in LLM-generated documentation. Hallucination refers to a condition where the AI produces information that sounds plausible but is not supported by the actual input data. In this project, unsupported AI output may appear in the form of unconfirmed root causes, repair actions, component failures, safety impacts, or operational conclusions.

For example, if the original fault record only states that a display refresh delay occurred, the AI should not automatically conclude that a specific data bus, software version, or avionics module is faulty unless that information is recorded in the source data. Similarly, if the root cause field is empty, the AI must not present a root cause as a confirmed fact. It may recommended that the engineer investigate the root cause, but it must clearly state that the root cause has not yet been confirmed. This verification is important because the system is used for aircraft fault management, where documentation accuracy effects communication between test engineers, maintenance engineers, and managers. Incorrect or unsupported information may create confusion during fault investigation and may weaken the reliability of the closed-loop workflow. Therefore, the AI response must be evaluated using a method that checks its relationship with the original fault record. Automated evaluation metrics such as BLEU or ROUGE, commonly used for natural language generation tasks, were considered unsuitable for this context because they measure surface-level textual similarity to a reference text rather than factual correctness against structured fault data. Since no reference “ground-truth description” exists for a newly reported fault, an expert-based manual verification approach was adopted instead, in which the generated content is checked directly against the source fault record rather than against a fixed reference text [9]. The AI Helper module was developed to assist engineers in generating fault descriptions and maintenance explanations based on the fault information entered into the system. Although large language models are capable of producing coherent and contextually relevant text, they may occasionally generate unsupported or inaccurate information, commonly referred to as hallucination. Therefore, an additional verification process was conducted to evaluate the reliability of AI-generated responses.

This study adopted an Expert-based Manual Verification method. In this method, each AI-generated response was manually compared with the original fault record stored in the system. The verification focused on determining whether the generated content accurately reflected the available fault information without introducing unsupported technical details. Unlike fully automated evaluation metrics, manual verification is considered more appropriate because the objective of the AI module is to assist documentation rather than make autonomous maintenance decisions. Therefore, the correctness of the generated response must always be assessed against the actual fault record. Ten fault records representing different aircraft subsystems were selected for verification. For each fault record, the AI Helper generated a fault description or maintenance explanation. The generated response was then evaluated using four predefined verification criteria.

Each criterion was evaluated manually. A response satisfying all four criteria was classified as Accepted, while responses containing unsupported assumptions or inaccurate technical information were classified as Needs Revision. 4.8.3.2 Source-Grounded Manual Verification Method This study used Source-Grounded Manual Verification to evaluate the correctness of the LLM-generated responses. The term source-grounded means that the AI answer must be grounded in, or traceable to, the original source data. In this system, the source data refers to the fault record stored in the database, including aircraft identity, aircraft model, subsystem, severity level, current workflow status, fault description, component affected, flight phase, environmental conditions, analysis findings, root cause, and resolution action. This method was selected because the AI module in this project is used for documentation assistance rather than autonomous decision-making. The correctness of the AI output cannot be judged only by grammar, fluency, or writing quality. A response can be well-written but still incorrect if it adds technical claims that are not available in the original fault record. For this reason, each generated response was manually compared with the source data. The verification process checks the AI response sentence by sentence. A statement is considered supported if it matches the original fault record or an engineer-confirmed field. A statement is considered contradicted if it conflicts with the original record. A statement is considered unsupported if it introduces a root cause, repair action, component failure, safety impact, or operational conclusion that is not present in the source data. If unsupported or contradicted information is found, the response is classified as Needs Revision.

Automatic text-generation metrics such as BLEU or ROUGE were not used because they mainly measure similarity between generated text and a reference text. In this project, there is no single fixed reference answer for each fault record. Different explanations can be acceptable as long as they remain faithful to the database record. Therefore, manual source-grounded verification is more appropriate for evaluating factual correctness and hallucination risk. An AI answer was considered correct only when all important statements could be traced back to the original fault record or to engineer-confirmed analysis fields. This rule ensures that the AI output remains a documentation aid and does not become an uncontrolled source of technical assumptions. 4.8.3.3 Rule-Based Automated Grounding Validation In addition to Source-Grounded Manual Verification, this study added Rule-Based Automated Grounding Validation as a supporting evaluation method for the AI Helper module. The purpose of this method is to provide a repeatable check to ensure that AIgenerated responses remain grounded in the original fault record. This method does not replace manual verification, but it helps detect common issues before the response is accepted.

The automated validation was inspired by Natural Language Inference (NLI)- based factual consistency evaluation. In NLI-based evaluation, the source data can be treated as the premise and the generated answer can be treated as the hypothesis. A generated statement is considered supported when it can be verified from the source, contradicted when it conflicts with the source, and unsupported when it introduces information that is not available in the source. In this project, the NLI concept was adapted into a rule-based validation method because the source data is stored as structured fault records in the database. The validation checks whether the AI response includes confirmed information from the source record, handles missing fields correctly, follows the required response structure, and avoids unsupported technical assumptions such as unverified root causes, repair actions, component failures, operational impacts, or safety conclusions. The original fault record was used as the grounding source for each AI response. The fields used for grounding include aircraft identity, aircraft model, subsystem, severity level, current workflow status, fault description, affected component, flight phase, environmental condition, analysis findings, root cause, and resolution action. When a field is not available in the source record, the AI response is expected to explicitly state that the information is not confirmed instead of generating an assumption. The automated validation process is illustrated in Fig4.xx. The process starts by retrieving the source fault record and the corresponding AI-generated response. The response is then evaluated using predefined grounding rules. If all rules are satisfied, the response is classified as Pass. If one or more rules fail, the response is classified as Fail and must be reviewed before being accepted.

4.8.3.11 Discussion The comparison between the initial evaluation and the evaluation after improvement shows that source-grounding is important when using LLMs in aircraft fault documentation. Before the improvement, the AI-generated response could sound technically reasonable but still include information that was not supported by the source record. This type of output is risky because readers may assume that the AI-generated explanation has already been verified by an engineer. After the improvement, the AI output became more controlled and easier to verify. The Confirmed From Record section limits the response to data that exists in the system database. The Not Confirmed section explicitly identifies missing information, such as analysis findings, root cause, or resolution action. The Recommended Checks section provides next-step guidance without presenting the guidance as a confirmed technical conclusion. The combination of manual verification and automated grounding validation strengthens the evaluation of the AI Helper module. Manual verification is important because aircraft fault documentation requires technical judgment and contextual understanding. Automated validation is useful because it provides a consistent and repeatable way to detect common grounding problems. Therefore, the correctness of AI-generated responses is ensured through multiple layers: prompt-level control, automated rule-based validation, and final human verification. Although the automated validation improves the reliability of the evaluation process, it does not fully replace manual review. Rule-based validation can detect predefined patterns of unsupported information, but it cannot understand every possible technical context. For this reason, the AI response is still treated as an editable suggestion that must be reviewed by the responsible engineer before being used in formal documentation.

In conclusion, the hybrid evaluation approach provides a practical way to evaluate LLM output in this project. It directly addresses whether the AI answer is correct and explains how correctness is ensured. The method also demonstrates that AI output should be treated as an editable suggestion, not as final engineering documentation without review.

#### 4.8.4 Testing Summary

The testing process confirmed that the system functions are able to support the aircraft fault closed-loop workflow. Functional testing verified that users can record faults, update workflow status, manage analysis information, and generate reports according to their role. In addition to functional testing, AI response verification was conducted to evaluate whether the AI Helper module produces responses that are correct, relevant, and grounded in the original fault data. The AI response evaluation showed a clear improvement after the prompt and response format were revised. The initial manual evaluation showed that only 25% of the evaluated responses were accepted because some responses contained unsupported technical assumptions. After adding source-grounding rules and a structured response format, the manual verification result improved to 100% on ten representative test cases.

This indicates that the revised AI response design made the output easier to verify and reduced unsupported information. The automated grounding validation further strengthened the evaluation by expanding the test to forty fault records. The result showed an Automated Grounding Pass Rate of 100.0% and Missing Field Handling Accuracy of 100.0%. This means that the AI responses passed the predefined validation rules and consistently marked unavailable information as not confirmed. These results support the conclusion that the AI Helper module can assist documentation while maintaining traceability to the source fault record. Overall, the testing results demonstrate that the system not only supports the closed-loop management of aircraft test faults, but also includes controls to ensure that AI-generated documentation remains reliable. The combination of functional testing, manual AI verification, automated grounding validation, and human-in-the-loop review provides a stronger basis for accepting the system as suitable for its intended purpose.

#### Conclusion

#### Project Achievements

The project has been successful in implementing the Web-Based Aircraft Test Fault Closed-Loop Management System. All the six goals outlined at the beginning of the project have been successfully achieved through the implementation of the proposed solution. The development of a centralized fault management system allows authorized users to perform operations such as creation, viewing, updating, and tracking of the faults via a standardized process. A seven-stage workflow process ensures that every fault undergoes seven stages within its lifecycle, ensuring that only valid transactions occur, and all faults must be validated before they can be classified as closed. Four user roles were created for this project, with each having a unique set of permissions. This allows each user to access sensitive data only at the viewing stage. The modules in dashboards and reporting provide graphical representation and filtered view of the fault data. It allows managers to monitor the fault trends, aircraft hotspot and overdue activities. Integration of the AI assistance module with the OpenRouter API to create fault description and summary works successfully, with a backup plan that ensures continuity when the API is not available. All fifteen functional test cases were successful with no major defects found. All the business rules were implemented successfully and have been tested. The system functions efficiently.

#### Limitations

Although the system achieves its purpose, there are a few limitations that need to be noted: (1) The system lacks an interface with other aircraft avionics or sensor data systems. Every piece of data regarding aircraft faults is entered manually, which can potentially lead to mistakes during the data input stage. (2) A feature for exporting reports into file format (PDF, CSV, etc.) was not included in this release. Report pages can only be saved by using the print function of a web browser. (3) The AI assistant module is reliant on the availability and pricing of an OpenRouter API. While the secondary solution still works, it cannot provide a level of contextual answers comparable to the ones provided by AI. (4) The system has been developed and tested in a development environment; however, no performance and security testing has been performed yet to ensure that it can be deployed for production use. (5) The notification and alert function has not been added to the system in its current state.

#### Future Improvements

Recommendations for improvement based on project deliverables and constraints are: (1) Exporting capability: Integrate export capability to export fault records and reports in PDF or CSV formats. (2) Email notification system: Integration of an email or similar notification system which will notify an engineer that he has been assigned to a fault, or his fault is overdue, and any other activity on the fault. (3) Predictive maintenance analysis: Using data from past faults occurring, analyze the data to predict faults in the future considering aircraft, subsystem, flight phase, and environmental factors. (4) API Integration of aircraft systems: Design integration connectors to obtain fault data from the systems in real time without requiring manual data entry. (5) Mobile-optimized interface: Further optimizations can be done to the interface making it more mobile-friendly so that engineers can use the application on tablet computers. (6) Production readiness: Perform load testing, security auditing, and compliance checking to ensure system is production ready and can be put through test in the aviation industry.
